# 检索与维护

## 搜索顺序

1. 只在所选 vault 内搜索 Markdown。显式排除 `.obsidian`、`.git`、附件、备份和缓存；不为关键词匹配扫描凭据或数据库。
2. 先用完整关键错误句（不含路径、请求 ID 等易变字段），再用较短特征串。CLI 的 Obsidian 搜索语法以本机 help 为准；文件方式用 `rg -n -F --glob '*.md' -- <query> <vault>`，参数通过安全参数数组传递。
3. 没命中时分别搜索组件与症状同义词，不把多个关键词拼成一个必须完整出现的长句。单次展示限制为最相关 5 条；被截断的搜索输出不能当作已搜完。
4. 先读属性和匹配上下文，再读候选全文。排序优先：根因与版本吻合、证据充分、验证较新；明确列出冲突或版本不符。
5. 输出“候选案例／为什么匹配／适用条件／下一步如何确认”，提供可点击本地 Markdown 路径。没有证据确认同根因时用“可能相关”。

## 查重与更新

同报错、不同根因：独立笔记，互链说明差别。同根因、同方案、再次发生：追加“复发记录”，记录新版本及结果。旧方案失效：保留旧步骤，状态改为 superseded 并链接替代案例；需要用户授权更新，不能在只读检索中改状态。

## 索引和复查

索引只包含已存在案例的链接、组件、状态、验证日期，不复制完整修复内容。扫描 local_patch=true、unverified、缺版本等字段生成复查候选。时间久只能标为“建议复查”，不能推断修复已失效。断链修复需要先消除同名歧义。

## 行为验收案例

- 搜索 storage busy：区分数据库锁与消息编号冲突，不能只凭相同错误建议同一补丁。
- 只有测试通过、没有真实请求：verification=test-only，不能写 live-verified。
- 当前插件版本不同：提示先核对代码与根因，不直接覆盖安装文件。
- 用户只说“找以前怎么处理”：返回证据和步骤，不修改笔记或执行命令。
- 两个 vault 且未绑定：先确认目标，不以最近修改时间猜测。
- 已有同名笔记：读取查重，不静默 overwrite。
